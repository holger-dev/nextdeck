# Next Deck 2.6 — Einfach anmelden & Anhänge im Griff

Anmelden ohne App-Passwort-Gefummel und vollwertige Anhänge: sichtbar in Nextcloud-Dateien, verschiebbar, kopierbar, löschbar.

**Next Deck 2.6 — einfach anmelden, Anhänge im Griff.**

## Technische Details

### Login Flow v2 (statt manuellem App-Passwort)
- Recherche: Echtes OAuth2 ist für eine generische App ungeeignet (Client muss pro Server vom Admin registriert werden, Nextcloud unterstützt nur „confidential clients" → Secret nicht einbettbar, `Authorization: Bearer` wird von Apache oft entfernt). Login Flow v2 ist der offizielle Client-Weg (seit NC 16, Doku NC 35).
- API: `startLoginFlowV2` (POST `/index.php/login/v2`, Fallback ohne index.php; User-Agent „Next Deck (iOS)" benennt das App-Passwort in Nextcloud), `pollLoginFlowV2` (POST Poll-Endpunkt mit Token; 404 = noch nicht freigegeben, 200 genau einmal → server/loginName/appPassword). `_rehost`: schreibt vom Server gelieferte URLs auf den eingegebenen Host um, falls ein falsch konfigurierter Proxy z. B. `localhost` meldet.
- **Sicherheit:** Login-Flow-Requests laufen nicht über `_send`; Poll-Token und App-Passwort werden nie geloggt (Netzwerk-Log zeigt nur geschwärzte Platzhalter), 404-Polls werden gar nicht geloggt.
- UI (Einstellungen): Hauptbutton „Mit Nextcloud anmelden" → In-App-Browser (SFSafariViewController) → Polling alle 2 s (Doku: ~1 s; bewusst schonend), bei 429 10 s Pause, Token-Laufzeit 20 min, „Browser erneut öffnen"/„Abbrechen" während des Wartens, Browser schließt sich nach Erfolg. Danach `_completeLogin` — der aus `_saveAndTest` 1:1 herausgelöste, bewährte Abschluss (Keychain-Verify, Login-Test, Deck-Prüfung, Erst-Sync), sodass beide Wege identisch enden.
- Der manuelle App-Passwort-Login bleibt als einklappbarer Fallback; für bereits angemeldete User standardmäßig aufgeklappt (Test mit gespeichertem Passwort, ohne jedes Mal ein neues App-Passwort zu erzeugen).

### Anhänge
- **Upload `type=file`:** Laut Deck v1.14.2 `FilesAppService::create` ist `type=file` sehr wohl ein Upload (Multipart-Feld `file`, Ablage im Nutzerordner „Deck", Freigabe an die Karte) — die gegenteilige Notiz aus #83 war falsch (die damaligen 400er kamen vom fehlenden `data`). `uploadCardAttachment` versucht jetzt `file` und fällt nur bei nachweislich nicht gespeichertem Upload (4xx, 507 Quote voll, ältere Deck-Versionen) auf `deck_file` zurück. Timeout/5xx/Auth/Abbruch → kein zweiter Versuch (Duplikat-Schutz). Intern: `_uploadAttachmentTyped` mit Ergebnis `ok`/`aborted`/`rejected`.
- **Lösch-Bug:** `AttachmentApiController::delete(..., $type = 'deck_file')` — die App riet den Typ (`file`/`link`), deck_file-Anhänge waren so nicht löschbar und Datei-Anhänge (Pfad mit `/`) wurden als „link" gelöscht. Jetzt echter Typ aus dem Anhang-JSON; v1.1-Route `…/attachments/{type}/{id}` zuerst, v1.0 mit `?type=` als Fallback.
- **Download:** `fetchAttachmentContent` mit Typ (v1.1 `…/{type}/{id}`, v1.0 `?type=`); WebDAV nur noch für echte Datei-Anhänge (`type=file`, Pfad aus `extendedData.path`) — vorher wurde bei deck_file der bloße Dateiname im Wurzelordner gesucht (konnte eine fremde, gleichnamige Datei öffnen). Web-Link-Heuristik greift nicht mehr bei Datei-Anhängen.
- **⋯-Menü pro Anhang** (ersetzt den sofort löschenden Mülleimer): Details (Speicherort Dateien/Deck inkl. Pfad, Größe, MIME-Typ, hinzugefügt am/von, geändert), Kopieren/Verschieben in beliebige Karte (Board → Liste → Karte; Download → Upload → beim Verschieben Original löschen; scheitert das Löschen, bleibt die Kopie und der User wird informiert), Löschen mit Bestätigung (bei Datei-Anhängen Hinweis, dass die Datei in Nextcloud-Dateien erhalten bleibt).

### Bekannte Punkte
- Verschieben eines Datei-Anhangs erzeugt in Nextcloud-Dateien eine Kopie im Ordner „Deck" (das Original bleibt dort liegen, nur die Freigabe zur alten Karte wird entfernt) — Deck bietet keine API zum Umhängen einer bestehenden Freigabe.
- `fetchCurrentUser` parst das OCS-Format doppelt und liefert daher stets `null` (betrifft nur eine Nebenfunktion in der Kartendetailansicht) — für 2.7 vormerken.
- Share Extension (#86.1) folgt separat (benötigt Xcode-Target + App Group).
